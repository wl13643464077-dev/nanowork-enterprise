## 一、第一性原理：这个产品到底在为实体店老板解决什么

**第一性拆解：实体店老板的生意 = 客流 × 转化 × 客单 × 复购 − 成本 − 风险。**
老板缺的不是"软件"，是**没时间、没专业团队、请不起顾问**。所以每个功能只有一个存在性检验标准：
**它是否用老板付得起的价格，替代了一个老板请不起的人？**

逐模块过（✓=通过第一性检验 / △=方向对但打折 / ✗=存疑）：

| 模块 | 替代的是谁 | 检验 | 判断依据 |
|---|---|---|---|
| 驾驶舱 | 数据分析师 | △ | 指标真实、按权限隔离 ✓；但数据靠 Excel 导入，老板"没时间"这关没过——数据不自动进来，看板就会荒废。**整改：优先接一个自动数据源（哪怕只是收银机日报邮件解析）** |
| 60 位餐饮员工 | 各领域顾问 | ✓ | 岗位手册真实专业（选址测算/HACCP/菜单工程都是行业真方法论）；单次 0.05–2.4 元 vs 顾问咨询 500+/小时，价差 3 个数量级，这是产品的核心杠杆 |
| 内容生产仓 10 员工 | 内容代运营团队 | ✓ | 对标外包 300–1500 元/篇；有输出契约+人工审核+不自动发布，边界诚实 |
| 经营工具箱 8 件 | 营销助理 | ✓ | 已接真 AI；绑定具体岗位员工；"今日必发"这类高频工具是留存钩子 |
| 活动闭环 | 策划+执行督导 | ✓ | 26 接口全闭环，复盘回流知识库，是全站逻辑最完整的模块 |
| 增长中心 CRM | 会员运营 | △ | 功能完整，但"线索"模型偏 toB 销售话术（沟通/邀约/到店/成交），餐饮老板的语言是"新客/回头客/储值会员"。**整改：术语与漏斗按餐饮重命名**（LEGACY_ALLOW 台账里那 21 处旧术语正是此问题） |
| 知识库+RAG | 店务资料柜 | △ | 机制完整（向量检索+引用溯源+degraded 不冒充），但**实测当前租户零向量、注入已停用**，等于摆设。**整改：向量回填做成后台自动任务，不要靠人跑脚本** |
| 积分计费 | —（商业模式本身） | ✓ | 两阶段预授权是全项目最硬的工程资产：不超卖、未交付全退、异常留对账。收费敢这么设计说明对交付有信心 |
| 权限体系 | —（企业治理） | ✓ | 四层：模块→功能→部门→员工派活（第十轮补齐），老板/管理员永不锁死 |

**第一性结论**：产品主轴（便宜地替代请不起的人）成立，60+10 员工 + 工具箱 + 活动闭环是真价值。最大的第一性缺口不是功能，是**数据入口**——一切分析类价值都建立在"老板会持续把数据喂进来"这个不成立的假设上。

## 二、对抗性评审：往死里打，哪里会塌

### P0（会直接砸口碑）

1. **真实通道下单独派活的交付成功率未校准。**
   实测：老板给食安员工 #117 派活，模型输出 9852 字符 → 输出契约校验不合格 → 自动重试（repair）→ 二轮仍不合格 → **10 分钟后任务标"失败"**。
   计费上退了钱（两阶段兑现了承诺），但老板视角是"等了10分钟，员工交白卷"。连续两次就会卸载。
   **整改**：
   - 按模型档位分契约严格度：flash 级模型用宽松契约（Markdown 结构即可），gpt-5.5 才用严格 JSON 契约；
   - repair 重试不要从零重生成，把首轮产物+校验错误一起给模型做增量修复（省一半时间）；
   - 失败时把"已生成的不合格草稿"以「未达标草稿」形式给老板看，比空手而归好得多。

2. **RAG 零向量静默降级。** 机制诚实（标 degraded），但没有任何主动修复路径——不会自动回填，也不提醒管理员。知识库越用越多、检索永远走热度兜底。
   **整改**：服务启动/文档入库时检测无向量→自动排队回填；系统页给管理员一个红点。

3. **员工目录数据是演示种子。** `SEED_DEMO` 之外，新租户开通后驾驶舱/增长/活动全是空的，而空状态引导（"下一步产生数据"）覆盖不全。新客户第一小时的体验决定续费，当前第一小时是空白仪表盘。
   **整改**：新租户首登强制走"开店向导"：门店基础信息 → 传一份菜单 → 派第一单活，10 分钟内让老板拿到第一份 AI 交付物。

### P1（竞争对手会攻击的点）

4. **数据孤岛**：无收银/外卖平台对接（客如云、美团的主场优势）。短期打不过就不打：定位为"平台之上的 AI 层"，先把 Excel 导入的摩擦降到最低（拍照识别报表、微信转发账单）。
5. **单店视角**：tenant=企业但无门店维度表，连锁老板（最有付费能力的客群）用不起来。督导巡店功能（本轮新增）正好倒逼补门店模型。
6. **移动端弱**：老板的真实终端是手机，`/m` 页面功能覆盖率低。派活审阅这两个高频动作必须手机可完成。

### P2（工程债）

7. 派活是异步任务但前端轮询感知慢（食安任务失败后工作台还显示"生成中"直到刷新）；应在任务状态翻转时主动推送（已有 SSE 基建）。
8. `agent_tasks` 无 fail_reason 字段落库，失败原因只在内存/日志，客服排查全靠猜。
9. JWT_SECRET 未配置时用随机密钥（重启全员掉线）——生产部署检查清单要挡住这个。

## 三、用户视角体验走查（以"川菜馆老板娘，45 岁，手机为主"人设）

| 触点 | 体验 | 判断 | 改进 |
|---|---|---|---|
| 登录页 | 信息量大（闭环图+行业词+星阵） | ✗ 太"科技发布会"，老板要的是"快进去干活" | 学 Claude/GPT：极简居中卡片，一眼找到输入框（本轮重做） |
| 员工目录 | 真人头像+ROI 条（第十轮后） | ✓ 头像立住了"员工"心智 | 区间数字太宽读不懂 → 改"约 X 积分/次、约 ¥Y/月"（本轮） |
| 员工工作台 | 七个 Tab 全是长文本 | ✗ 像内部技术文档，老板只想"把活派出去" | 卡片化+把「派活」放 C 位（本轮重做） |
| 派活等待 | 有阶段进度（第九轮） | △ 但失败要等10分钟才知道 | 见对抗性 #1、#7 |
| 内容生产仓 | 流水线可视化 | ✓ 全站最好的一页 | 无 |
| 工具箱 | 表单直给 | ✓ | 高频工具（今日必发）加"一键用昨天的输入" |
| 充值 | 对公/人工确认 | △ 小老板习惯扫码 | 接扫码支付前至少把"联系客服"做成一键微信 |

**体验主判断**：系统的"诚实工程"（不冒充、可追溯、不自动外发）是 B 端的核心信任资产，但表达方式太工程师化——老板不需要看到"契约ID/档案指纹/修订哈希"，这些应折叠进"详情"，前台只留人话。
