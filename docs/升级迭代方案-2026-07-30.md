## 1. 诊断结论：真正的问题不是"实习生审美"

问题分三层，越往下越贵，但只有底层修了上层才不会反弹。

**表层（看得见的"垃圾感"）**
- 字号从规定的 7 档扩散到 **25 个值**，含 8px / 9.5px / 10.5px 等 82 处低于底线的值
- 2,198 处内联 `style={{`，其中 866 处硬编码字号、995 处硬编码间距；token 只被引用 30 次
- 语义色三套并存：`--danger: #f25b6b`、`Kit.tsx:87` 的 `#ef4444`、`Employees.css` 的第三套
- 13 个业务页面（驾驶舱 / 内容工厂 / 今日经营 / 经营洞察…）**零关键帧动画**，13 个 `@keyframes` 里 6 个在登录页
- `transition` 全项目仅 19 处，`:active` 零命中——用户 95% 的使用时间面对一个完全静止的界面

**中层（交互逻辑不成立）**
- 60–135 秒的 AI 长任务只有一个转圈：`ContentFactory.tsx:3405`、`Dashboard.tsx:2267`。26 处 `<Progress>` 全部用于业务指标，**零处用于任务进度**
- 后端 `yunwu.chatStream` + `ai.generate({onDelta})` 流式链路早就通了，前端 `api.stream` **只有 `Advisor.tsx` 一处在用**；`Dashboard.tsx:308` 调同一个已支持流式的员工对话接口，走的却是 `api.post` 干等 135 秒
- 错误态三套实现、空态 87 处各写各的、成功提示 175 次全走 toast（`notification` 零使用）
- 全项目只有 1 个 ErrorBoundary，粒度是整个 App——任一页面渲染异常白屏整站
- 13 个一级菜单零分组；`/toolbox` 与 `/content` 共用同一权限模块却是两个入口；无面包屑、无全局搜索、无命令面板

**底层（架构欠账，是上面所有问题的成因）**
- 自研 `useQuery` 设计正确（版本号防竞态 + 卸载作废），但**只覆盖 2/13 个页面**；其余约 190 个 API 调用手写四态，轮询逻辑手写 11 遍
- 5 个文件超 2,700 行。`ContentFactory.tsx` 4,999 行 / 55 个 useState / 单个 return 2,985 行 JSX / **0 个 useMemo**；`Growth.tsx` 58 个 useState；`System.tsx` 把 8 个 Tab 的 JSX 全部提前求值，不可见的 7 个也参与每次渲染
- `React.memo` 全项目 1 处；零虚拟化；所有 Table 的 `columns` 内联字面量（`Admin.tsx` 18 处），每次渲染重建全部 render 闭包
- 首屏 **36 个请求 / 323 KB gzip**，34 个 modulepreload 里塞着 antd 的 Input、tag、modal、form 和 13 个图标 chunk
- 前后端契约纯手写：830 处 `: any`，255 个端点里有 TS 类型的不到 10 个，无 OpenAPI / zod。改后端字段**不会有任何编译期报错**
- 无 CI。61 张表的多租户隔离扫描和 491 个测试断言，全靠手工记得跑

**一句话**：UI 难看是症状，`theme.css` 写了规矩但没有执法机制、Kit 只有 9 个导出撑不住 13 个页面、没有数据层导致每个页面自己造一遍轮子——这三件才是病根。

## 3. 升级原则（每条都可被测试验证）

1. **规矩要有执法机制。** 只写 `theme.css` 没用，必须加 stylelint + ESLint 自定义规则 + CI 卡住，否则三个月后又长回 25 档字号。
2. **能力优先于装饰。** 后端已就绪但前端没接的（流式、`/agents` 7 个端点）先接上，收益最大成本最低。
3. **诚实化不可退让。** 无数据返回 null 不估算、配置存在 ≠ 已验证、模板降级必须显式标记——这是项目的核心资产，动效和视觉升级不得掩盖任何一条。
4. **`EmployeeWorkbench.tsx` 是范式。** 2,114 行但主 return 仅 186 行、20+ 纯函数 + 8 子组件 + 独立 CSS + 仅 11 处内联样式。所有巨型文件按它重构。
5. **DESIGN.md 是硬约束。** 色板不可自选、导航按老板任务命名、三条禁止项已被回归测试固化。视觉升级在这个笼子里做。
6. **每期可独立发布。** 不做需要一次性全改完才能跑的大爆炸重构。

## 4. 六条工作流

### W1 · 设计系统落地与执法

- `theme.css` 扩容为三层 token：primitive（色阶 / 字阶 / 间距）→ semantic（`--text-primary` / `--surface-raised` / `--status-*`）→ component（`--kpi-card-pad` / `--table-row-h`）
- 新增**密度模式**（comfortable / compact），老板笔记本和门店大屏用同一套组件不同 token
- 统一断点为 640 / 820 / 1024 / 1280 / 1536，废掉现存的四套并行断点（MainLayout 1320/1180/1000/820、Employees 1500/1180/760/640/520、Toolbox 1380/900/620）
- 语义色去重：`#ef4444`、`#22c4a8`、`#8a7450` 等 7 个野色收进 token；图表调色板补 midnight 深色变体
- **执法层**：stylelint 禁硬编码色/字号/间距；ESLint 自定义规则限制 `style={{}}` 中的字面量；CI 跑一个"token 落地率"脚本，内联样式数量只允许下降不允许上升

### W2 · UI Kit 扩容（Kit.tsx 9 个导出 → 约 30 个）

补齐现在被各页面重复实现的一切：`PageHeader`、`EmptyState`、`LoadingState`、`DataTable`（含 sticky 表头 / 列固定 / 批量操作 / 记忆化 columns / 虚拟化开关）、`FilterBar`、`DrillDrawer`（顶部固定数据口径，落实 DESIGN.md 第 34 行）、`MetricCard`、`SectionHeader`、`StatusPill`、`ProgressTask`、`StreamingOutput`。

顺手消灭已确认的重复：`RuntimeReadinessMatrix`（64 行 × 2）、`readinessTag`（× 2）、`loadSourceMap` + `openSourceSample`（28 行 × 2）、`KIND_LABEL`（× 2）、区块标题（3 套）、指标卡（3 套）、`ErrorState`（2 套视觉）。

### W3 · 信息架构与导航

- 13 个扁平菜单重组为 4 组：**看数据**（驾驶舱 / 经营洞察 / 门店数据）· **派活干活**（数字员工 / 今日经营 / 营销活动 / 会员增长）· **内容生产**（内容生产仓 / 经营工具箱 / 知识资产）· **配置**（系统管理 / 充值中心）
- **Cmd+K 命令面板**：导航跳转 + 实体搜索（客户 / 活动 / 员工 / 内容 / 资产）+ 快捷动作（派活给…、生成…）+ 最近访问。目标首屏渲染 < 150ms
- 面包屑 + 页头统一（当前 `MainLayout` 页头与各页自写标题形成双标题）
- 理清 `/toolbox` 与 `/content` 的边界：工具箱是"单次输入换单次交付"，内容生产仓是"10 工位流水线"。权限模块拆开，入口文案说清差别
- 顶栏三条硬编码静态状态文案（`岗位档案 70岗` 之类）换成真实可点的状态入口；干掉 `nth-of-type(n+2)` 这种脆弱隐藏

### W4 · 数据层与巨型文件治理

- 引入 **TanStack Query v5**：query-key 工厂 + `queryOptions` 集中定义 + 显式 `staleTime`，服务端状态归 Query、UI 状态留在组件。`useQuery.tsx` 保留为兼容壳逐步下线
- 收掉 11 处手写 `setInterval`（5 种间隔）为 `refetchInterval` + 现有的可见性门控
- 巨型文件按 `EmployeeWorkbench` 范式拆解，目标单文件 < 600 行：
  - `ContentFactory.tsx` 4,999 → 6 个 Tab 各自独立模块 + 共享 hooks
  - `System.tsx` 3,567 → 8 个 Tab 懒加载（当前不可见的 7 个 Tab JSX 也在每次渲染时求值）
  - `Activities.tsx` / `Growth.tsx` / `Execution.tsx` / `Dashboard.tsx` / `Admin.tsx` 同理
- 记忆化补齐：Table columns 全部 `useMemo`、图表 option 全部 `useMemo`（现在每次渲染触发 `setOption(notMerge=true)` + 近百次 `getComputedStyle`）、子组件按需 `React.memo`
- 长列表虚拟化；`Assets.tsx:299` 和 `MainLayout.tsx:211` 的固定 `size=100` 改真分页
- 打包：首屏 modulepreload 瘦身、`chunkSizeWarningLimit` 从 1600 收回、加 bundle 分析、echarts 按图表类型二次拆分
- 路由级 + Drawer 级 ErrorBoundary（现在只有 1 个 App 级）

### W5 · 交互与动效体系

**这是"动效很垃圾"的正面回答。原则：动效服务于理解状态，不做炫技。**

- **流式输出**：`Dashboard.tsx:308` 立刻换 `api.stream`（后端零改动）；`content/generate`、`toolbox/runs`、`employee-workbench/*/dispatch` 等 20+ AI 端点接 `onDelta`（引擎层已就绪）。同时处理 advisor 现在"通道开了但增量在服务端缓冲到事务提交"的取舍——用两阶段交付保住资金安全的同时给出真实打字机效果
- **长任务进度**：AI 生成从"一个转圈"改为阶段化进度（检索 → 生成 → 校验 → 交付），骨架布局与最终结果一致（DESIGN.md 第 32 行要求）
- **骨架屏替代转圈**：5 处骨架 → 覆盖全部主要数据区；统一 `padding`（现在 24/30/32/36/40 五种并存）；骨架到内容 crossfade
- **微交互**：hover / focus / press 三态统一走 CSS class（内联样式写不了伪类，逼出了 `System.tsx:3028` 直接改 `e.currentTarget.style` 的反模式）
- **页面切换过渡**：路由级 fade + 轻位移，180ms，`--dur-*` / `--ease-out` 统一驱动（现在 `--dur-*` 零引用，19 处 transition 全硬编码）
- **列表 stagger**：`Employees.tsx` 已有的 `--enter-delay` 错峰模式推广到表格与卡片网格
- **数字滚动**：`AnimatedNumber` 实现完整却基本闲置（因为多数页面传 `fmtMoney()` 字符串走了不滚动分支），改造 `StatCard` 让格式化值也能滚
- **图表动效**：统一 `animationDuration` / `animationEasing` / `animationDelay` 与 token 对齐；启用已注册但没人开的 `AriaComponent`
- 全部动效受 `prefers-reduced-motion` 保护；无动效库依赖（CSS + rAF 足够，不引 framer-motion）

### W6 · 能力补齐（融合参考项目）

按第 2 节的取舍清单落地，优先级：

1. **全局任务中心**（新一级入口）——只读聚合现有 8 类任务，状态翻译成人话
2. **接通 `/agents` 前端入口**——后端 7 个端点已挂载且有测试，前端零调用，用户完全访问不到
3. **派单前对口预检**——70 员工点不准的问题，降级必须放行
4. **行业术语残留清理**——`Execution.tsx:75` 的「馆主」、`Activities.tsx:63-69` 存库仍是「品鉴会 / 回厂游 / 封坛仪式」而 label 已改餐饮词、`feishu.js:560` 与 `scoring.js:20` 的旧枚举、`db.js:918` 的「已到馆 / 已品鉴」。新写入统一餐饮口径，历史值走已有的 `LEGACY_*_MAP` 读时映射；反向断言测试补上前端常量表（现在只覆盖后端 payload）
5. **marshal / employees 双命名收敛**——`marshal` 一词现在同时指部门、员工、通知类型三种东西。`marshals` 表作为内部容器保留（有注释说明的有意决定），但**前端展示层与 API 命名统一为 employee**
6. 酒道馆 6 项服务端能力 + 4 个工程收口
7. 质检 Gate 概念层、发布 T+1/3/7 催复盘、行业知识底座多行业化

### W7 · 工程门禁（成本最低，收益最高，第一期就做）

- **GitHub Actions 跑 `npm run verify`**：79 个测试文件 / 491 断言 + tsc + 61 张表隔离扫描 + build，再加上现在没进 verify 的 `lint:strict` 和 `format:check`。半天工作量，把多租户隔离从"记得跑"变成"跑不过不能合"
- **前后端契约**：新增端点强制 zod schema 单一来源导出 TS 类型；老端点按页面迁移时逐个收（385 处 `res.json` 一次性全改风险太高，且 830 处 `any` 意味着改坏了不会报错）
- **响应体与分页收敛**：`pageParams` 覆盖率现在约 4%，`page/size` 与 `page/pageSize` 两套命名并存——新代码立约定，老代码渐进
- **可观测性**：仿 `obs.py` 做进程内指标（只记路由模板 / 状态码 / 耗时，不记业务数据）；前端回收 `X-Request-Id` 上报，把用户报错关联到服务端日志（后端已经在打这个日志，前端没接）
- **前端源码合同测试**：仿 paihuo 的做法锁死不变量（token 落地率、禁止文案、巨型文件行数上限）

## 7. 风险与不做清单

**风险**
- 巨型文件拆解是本方案最高风险项。缓解：一次只拆一个文件、拆完立刻跑 `accept-runtime.mjs`、每个文件单独提交可回滚
- 830 处 `any` 意味着重构不会有编译期保护。缓解：优先给被重构页面补类型，先类型后拆解
- 三条 DESIGN.md 禁止项已被回归测试固化，动视觉时会撞测试——这是好事，别改测试

**不做**
- 不推倒重写任何页面
- 不引入动效库（CSS + rAF 够用）
- 不做 385 处 `res.json` 的一次性响应体重构
- 不碰 PostgreSQL 迁移、RAG sqlite-vec 重构（原计划已列为需决策项）
- 不修改酒道馆 / paihuo-ai / 桌面参考项目的任何文件
- 不通过删条件或抬高验证层级把 CONDITIONAL GO 包装成 GO（沿用原有约束）
