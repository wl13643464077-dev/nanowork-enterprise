# 迭代复盘

日期：2026-07-31  
范围：纳米Work企业版本全功能回归、能力成熟度与第四轮生产可信度加固。

## 修复前基线

修复前项目具备完整页面骨架、70 名员工档案和大部分本地业务流程，但存在四类系统性偏差：

1. “目录或配置存在”被误当作“实际执行能力已生效”。
2. “有内容记录”被误当作“完成岗位交付”。
3. 单路由测试通过没有覆盖生产中间件、后台并发和两段式计费生命周期。
4. 本地流程可运行被误当作真实云雾、支付、飞书和发布渠道已经验收。

修复前发布判定为 **NOT GO**。

## 修复后迭代结果

- 外部调用先完成权限与预授权，后台并发租约保持到真实终态。
- 内容员工模型、长度、超时、技能、工作方式、提示词和岗位档案进入同一执行快照。
- 强制联网岗位必须取得可引用证据，失败不能冒充完成。
- 10 类内容输出契约从“只查字段名”升级为严格结构验证。
- 模板与契约底稿明确为未完成，不进入正式产出统计。
- 内容员工采用“业务产物先落库、再结算”的顺序。
- 高影响权限、百分比语义、角色入口和工具箱范围问题进入回归保护。
- 内容仓固定模板只作为参考/草稿，不冒充实时 AI、实时扫描或真实经营数据。
- 内容自动化以 `202 + runId + pollUrl` 接单、按 `runId` 精确轮询和同次运行幂等复用；手动/定时执行统一撤权门禁，费用估算、占扣和生成模型一致。
- 支付链路拒绝重复关键节点，渠道结果绑定本地商户订单，微信签名响应执行五分钟新鲜度校验。
- RAG 后台任务完成执行前预授权、真实用量结算、共享并发、超时释放和服务重启恢复。
- 60 名餐饮员工逐岗位严格输出契约、合法样本和非法反例进入工作台、执行、采纳和审计。
- 409 项技能中餐饮 344 项、内容 65 项进入工作台、执行快照、提示词和前端，并用分层证据避免把目录验证写成效果验证。
- 历史实际 8 个 `catalog_only` 全部归零，13 项连接器运行登记完整，本地辅助可执行，真实采集/发布缺条件时 fail closed。
- 生产应用装配从启动副作用中分离，完整守卫链进入真实 HTTP 集成回归；数据录入 `system` 模块门禁修复。
- 8 通道只读运行就绪矩阵区分配置、启用、验证与实际状态，不再把“检测到配置”写成“已连接”。
- 占扣结算/释放只按数据库权威行执行；恢复覆盖停用租户并隔离单条坏记录和子系统故障。
- 第四轮定义的三项本地生产可信度缺口全部关闭。
- 最终自动化计数：`491/491` 通过，0 失败；全部静态质量门通过。
- 第四轮真实浏览器与服务健康最终验收通过：3107 最新服务健康；管理员和系统页显示 8 通道真实状态，无连接误报；新鲜浏览器 error 日志 0。

发布结论：

- 本地无密钥演示：**GO**。
- 自动化本地回归：**GO**。
- 生产：**CONDITIONAL GO**。

生产保留 **CONDITIONAL GO**：云雾、检索、支付、飞书和外部发布尚未使用轮换后的授权沙箱/生产凭证完成真实验收；持久化人工对账、异步视频后台主动轮询和高成本请求级幂等仍待完成。

## 做得好的地方

- 先保留真实联调和全功能回归作为修复前基线，避免修复后覆盖历史证据。
- 按“安全与成本 → 完整员工执行 → 业务权限 → 输出语义”排序，优先关闭高损失风险。
- 对内容员工采用 RED/GREEN：配置、联网、契约、模板、落库和结算均有明确失败反例。
- 没有为了取得“全绿”而发起额外真实付费调用或不可逆外部动作。
- 把生产发布拆成三级结论，避免 GO/NOT GO 二元判断掩盖真实边界。
- 把“实现、配置、启用、验证、有效状态”拆开，避免管理页面成为不可信的运维信号。
- 用数据库权威记录而非调用方快照决定资金终态，并让恢复任务对坏记录具备隔离能力。

## 可以改进的地方

- 项目早期应建立统一 AI Gateway 和后台任务租约，不应等到全功能回归才补。
- 员工目录、技能目录、连接器目录必须与可执行契约分层命名，避免 `catalog_only` 被理解为已接通。
- 模板数据从第一天就应使用 `draft/incomplete` 状态，正式统计默认排除。
- 路由测试应更多通过生产中间件链，而不是直接挂载 Router。
- 外部链路应在开发阶段准备固定沙箱账号、轮换流程和脱敏证据模板。
