# 迭代复盘

日期：2026-07-31  
范围：纳米Work企业版本全功能回归、能力成熟度与第四轮生产可信度加固。

## 修复前基线

修复前项目具备完整页面骨架、70 名员工档案和大部分本地业务流程，但存在四类系统性偏差：

1. “目录或配置存在”被误当作“实际执行能力已生效”。
2. “有内容记录”被误当作“完成岗位交付”。
3. 单路由测试通过没有覆盖生产中间件、后台并发和两段式计费生命周期。
4. 本地流程可运行被误当作真实云雾、支付、飞书和发布渠道已经验收。

修复前发布判定为 **NOT GO**。

- 外部调用先完成权限与预授权，后台并发租约保持到真实终态。
- 内容员工模型、长度、超时、技能、工作方式、提示词和岗位档案进入同一执行快照。
- 强制联网岗位必须取得可引用证据，失败不能冒充完成。
- 10 类内容输出契约从“只查字段名”升级为严格结构验证。
- 模板与契约底稿明确为未完成，不进入正式产出统计。
- 内容员工采用“业务产物先落库、再结算”的顺序。
- 高影响权限、百分比语义、角色入口和工具箱范围问题进入回归保护。
- 内容仓固定模板只作为参考/草稿，不冒充实时 AI、实时扫描或真实经营数据。
- 内容自动化以 `202 + runId + pollUrl` 接单、按 `runId` 精确轮询和同次运行幂等复用；手动/定时执行统一撤权门禁，费用估算、占扣和生成模型一致。
- 支付链路拒绝重复关键节点，渠道结果绑定本地商户订单，微信签名响应执行五分钟新鲜度校验。
- RAG 后台任务完成执行前预授权、真实用量结算、共享并发、超时释放和服务重启恢复。
- 60 名餐饮员工逐岗位严格输出契约、合法样本和非法反例进入工作台、执行、采纳和审计。
- 409 项技能中餐饮 344 项、内容 65 项进入工作台、执行快照、提示词和前端，并用分层证据避免把目录验证写成效果验证。
- 历史实际 8 个 `catalog_only` 全部归零，13 项连接器运行登记完整，本地辅助可执行，真实采集/发布缺条件时 fail closed。
- 生产应用装配从启动副作用中分离，完整守卫链进入真实 HTTP 集成回归；数据录入 `system` 模块门禁修复。
- 8 通道只读运行就绪矩阵区分配置、启用、验证与实际状态，不再把“检测到配置”写成“已连接”。
- 占扣结算/释放只按数据库权威行执行；恢复覆盖停用租户并隔离单条坏记录和子系统故障。
- 第四轮定义的三项本地生产可信度缺口全部关闭。
- 最终自动化计数：`491/491` 通过，0 失败；全部静态质量门通过。
- 第四轮真实浏览器与服务健康最终验收通过：3107 最新服务健康；管理员和系统页显示 8 通道真实状态，无连接误报；新鲜浏览器 error 日志 0。

发布结论：

- 本地无密钥演示：**GO**。
- 自动化本地回归：**GO**。
- 生产：**CONDITIONAL GO**。

生产保留 **CONDITIONAL GO**：云雾、检索、支付、飞书和外部发布尚未使用轮换后的授权沙箱/生产凭证完成真实验收；持久化人工对账、异步视频后台主动轮询和高成本请求级幂等仍待完成。

## 做得好的地方

- 先保留真实联调和全功能回归作为修复前基线，避免修复后覆盖历史证据。
- 按“安全与成本 → 完整员工执行 → 业务权限 → 输出语义”排序，优先关闭高损失风险。
- 对内容员工采用 RED/GREEN：配置、联网、契约、模板、落库和结算均有明确失败反例。
- 没有为了取得“全绿”而发起额外真实付费调用或不可逆外部动作。
- 把生产发布拆成三级结论，避免 GO/NOT GO 二元判断掩盖真实边界。
- 把“实现、配置、启用、验证、有效状态”拆开，避免管理页面成为不可信的运维信号。
- 用数据库权威记录而非调用方快照决定资金终态，并让恢复任务对坏记录具备隔离能力。

## 可以改进的地方

- 项目早期应建立统一 AI Gateway 和后台任务租约，不应等到全功能回归才补。
- 员工目录、技能目录、连接器目录必须与可执行契约分层命名，避免 `catalog_only` 被理解为已接通。
- 模板数据从第一天就应使用 `draft/incomplete` 状态，正式统计默认排除。
- 路由测试应更多通过生产中间件链，而不是直接挂载 Router。
- 外部链路应在开发阶段准备固定沙箱账号、轮换流程和脱敏证据模板。

## 第五轮复盘补充（2026-07-31）

本轮真实浏览器比静态测试多发现三类问题：首次建库组织树未回填、员工仍能看到并确认公司作战计划、根任务业务流只展开一层。三项都已转为首次启动、角色拒绝和三级递归回归测试，说明角色化产品必须用“第一次启动 + 真账号点击 + 权威数据库回读”验收，不能只依赖已有库或单层接口 fixture。

下一轮优先事项不变：轮换并受控验证云文本/检索凭据；随后完成持久化对账、异步视频主动轮询和统一高成本请求幂等。

### 本轮真正关闭的问题

1. 不再用 HTTP 200、“有内容”或本地模板作为成功标准；通过必须同时满足真实供应商、正 token、契约、持久化回读、人工审阅和账务终态。

3. 任务的“生成、质量、审阅、使用”被拆成独立语义；自动质检通过不再被误写成“人工已采纳”。
4. 驳回与预授权释放收进同一事务；只读对账显示隔离库 174 条 hold 全部为 `settled`，当前 `held=0`。
5. 审核动作改为跟随任务快照和组织范围，未授权用户不再看到可点的审核入口，平台超管不代替租户管理者做业务决策。

### 做得好的地方

## 最终真实收口复盘（当前权威，2026-07-31）

最终结果为 70/70 真实数字员工、70/70 质量审计、27/27 功能矩阵；最新完整 `npm run verify` 的服务端回归快照为 `696/696`，类型、隔离、token、UI 契约、严格 lint、格式和生产构建全绿。老板、管理层、员工真实账号浏览器行走通过，最新控制台错误 0，3107/3108 健康，预览库与 L5 隔离库当前 `held` 均为 0。

这次最重要的教训不是“多跑几次”，而是每个未完成都必须落到可复现的权威状态：

1. 真实点击发现了自动化未覆盖的员工排行榜跨用户泄漏；修复后增加角色范围回归，再用员工账号复验，而不是只改页面文字。
2. 历史演示记录不能因为“不好看”被删除，也不能继续占据待办队列。只有固定指纹、无真实/下游证据的异常记录允许幂等对账，本轮收敛 6 条内容、6 条审批、2 条员工任务和 4 条自动化运行，并保留操作日志。
3. “质检未通过”“待审阅”“可使用”必须来自同一状态机；普通任务与提交错位最终为 0，失败记录仍可追溯但不再伪装成可处理待办。
4. assets 401 经过定向、全资源、压力和鉴权/限流复验均未复现，因此正确结论是“当前不可复现并保留监测”，不是为了关闭问题而制造一次无依据代码修改。
5. 今日作战计划和待办数属于实时经营事实，不能复用种子期“8 条待审”或版本展示文案；所有角色页面都必须按权威数据库和组织范围即时投影。
6. 结构合法不等于事实可靠。content:9 必须拦截无来源百分比、权重、行业基准和阈值，同时允许“待补历史基线/由负责人设定”和有明确来源的事实；该边界已进入 `696/696` 回归。真实云浏览器复跑和人工内容审阅另行留证，不能由工程测试替代。

## 2026-08-28｜本机部署复盘

1. 3107 由 LaunchAgent `com.nanowork.api` 管理，旧进程收到 TERM 后会自动重启；后续本机部署应直接使用守护任务的重启机制并等待其健康，不再并行执行备用 `nohup`，避免无害但会污染日志的 `EADDRINUSE`。
2. 发布检查必须同时验证“构建产物哈希”和“真实服务返回哈希”。本轮两者一致，且 46 个引用资源全部返回 200，避免只看到进程存活就误判部署完成。
3. 运行配置必须以进程日志和环境为准，不能照抄历史状态文档。本轮确认调度器重启前后均为启用；生产迁移还需显式锁定 `TZ=Asia/Shanghai`、自动任务窗口与外部副作用授权。
4. 数据库在重启前使用 SQLite 在线 `.backup` 制作一致性快照并做完整性校验；该步骤保留为以后每次部署的固定门禁。

## 未完成任务追因复盘追加（2026-07-31）

复盘官 #7 到 #10 说明了“跑完”至少有四层：供应商是否返回、契约是否可信、账务是否闭合、业务是否批准。#7/#8 虽然云调用成功，但人工仍然正确驳回；#9 虽然实际消耗了供应商推理，但因为契约连续失败，系统正确地不创建内容并全额释放；只有 #10 同时满足真实 API、契约、账务和人工审批，才进入可使用并生成资产/知识记录。

这次补上的工程原则：

1. 历史技能可以完整保留供老板查看，但未验证算法、权重和阈值不能作为运行时事实喂给模型。
2. 重试必须知道具体失败原因、模型停止原因和是否截断，不能靠重复同一个宽泛提示词碰运气。
3. “待账务对账”是安全状态，不是失败的别名；在结算证据完整前，所有可消费动作都必须关闭。
4. 驾驶舱、内容仓、任务中心、工具箱、媒体和业务流必须共享同一权威状态，而不是各自翻译一套中文。
5. 真实云复跑、单元回归和人工内容审阅是三份独立证据，任何一份都不能替代另外两份。
