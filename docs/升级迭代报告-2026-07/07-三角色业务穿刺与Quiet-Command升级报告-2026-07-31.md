# 三角色业务穿刺与 Quiet Command 升级报告

日期：2026-07-31
项目：纳米Work企业版本（新项目）
结论：本地真实应用链通过；云端模型质量样本等待轮换后的新测试密钥，不复用已暴露旧密钥。

## 一、本轮解决了什么

本轮同时处理三类问题：

1. 以老板、运营管理层和一线员工三种真实账号走正式应用接口，验证任务是否能分层派发、接单、提交、驳回、重提、审核和关闭。
2. 把任务、数字员工运行、人工审阅、内容/素材/资产之间的真实关系做成可回看的“业务流”，不再用展示性箭头冒充数据已经串联。
3. 将全局界面重构为 Quiet Command：可收起导航、主工作区优先、经营助手按需打开；重点重做任务指挥台、餐饮数字员工、Paihuo 内容生产仓和员工目录。

## 二、三角色真实应用链结果

验收使用生产 `createApp` 装配、正式登录鉴权、中间件、SQLite 持久化和真实路由；数据库隔离，Scheduler、后台向量和所有外部凭据关闭。测试不是直接调用内部函数，也没有跳过权限层。

| 角色 | 实际动作 | 结果 |
| --- | --- | --- |
| 老板 | 创建经营目标任务并派给运营；最终审核运营汇总 | 通过 |
| 运营管理层 | 本人接单；把上级目标拆成员工子任务；驳回不合格结果；复核重提 | 通过 |
| 一线员工 | 只能看到本人任务；本人接单、提交和重提；不可审核、不可越权拆解 | 通过 |
| 同级员工 | 读取或操作他人任务 | 403/404，按预期拒绝 |
| 跨租户账号 | 引用或读取其他企业任务 | 404，按预期隐藏 |

闭环顺序：

`老板派发 → 运营本人接单 → 运营拆解 → 员工本人接单 → 员工提交 → 运营驳回 → 员工重提 → 运营审核 → 运营汇总提交 → 老板终审`

最终浏览器验收又发现并关闭了一个首次建库缺陷：原组织关系迁移早于演示用户写入，导致第一次启动时运营总监没有下级、第二次启动后才可能恢复。现在种子事务会一次性建立 `guan → yunying → sales1/sales2/sales3`，全新数据库第一次启动即可完成三级拆解。

本轮新增的业务不变量：

- 管理层不能替执行人接单，提交也只能由任务负责人本人完成。
- 运营总监不能审核自己负责的任务；老板保留最终审核权。
- 上级任务只有在“进行中”时才能拆解，子任务必须交给另一位执行人。
- 任一下级任务未完成，上级任务不能提交或审核通过。
- 上级任务已有下级任务时不能直接删除，避免业务链断裂。
- 上级已经完成时，不能只重开子任务；必须从上级开始恢复流程。
- 驳回回到“进行中”；审核人、审核时间、意见和历史提交均保留。
- 已完成任务重开必须由管理层填写原因。

## 三、业务数据如何真正串联

新增只读接口：`GET /api/business-flow/:sourceType/:sourceId`。

当前支持四种权威来源：

- `advisor_message`：老板参谋会诊结论 → 管理任务。
- `manual_task`：上级任务 → 下级任务 → 结果提交 → 审核终态。
- `restaurant_task`：餐饮数字员工任务 → 内容产出 → 审批 → 业务资产。
- `content_run`：Paihuo 内容员工运行 → 人工审阅 → 内容/素材沉淀。

接口按租户和组织树投影，仅返回业务节点的白名单字段。员工查看子任务时，只看到“管理层拆解任务”这一公开来源，不会拿到上级管理任务标题、完整提示词、岗位档案、能力、技能库或运行快照。

前端入口已经接到：

- 任务看板每张任务卡的“业务流”。
- 餐饮数字员工运行记录的“业务流”。
- Paihuo 内容员工运行记录的“业务流”。

人工任务穿刺已支持安全递归：根任务一次返回全部可见后代及各级提交，最多 12 层、200 个后代、600 条提交，并通过 visited 防循环。普通员工查看叶子任务时，无权父链只显示匿名“管理层拆解任务”，不返回真实标题、状态、时间、链接或内部编号。

## 四、老板参谋与审批断链修复

- 老板参谋“转任务”按同企业真实负责人解析；无法匹配时交给运营管理层，不再默认塞给老板。
- “转派分部”生成可接单的管理任务，不再制造没有 worker、永久停在“执行中”的假数字员工任务。
- 餐饮数字员工工作台和审批中心复用同一个审核领域命令。
- 通过或驳回在同一事务内同步任务、内容、审批、知识与资产；重复处理保持幂等。
- 普通员工不能审核；高风险或老板专审结果仍由老板侧处理。
- 普通员工不再读取或显示公司目标、今日作战计划和“待老板确认”；相关接口同时执行管理角色守卫，不能通过直接请求旁路创建公司计划任务。
- 全新组织树首次初始化即可完成老板 → 管理层 → 员工分派，不再依赖第二次启动。

## 五、岗位内部档案与模型回显保护

- 只有老板、管理员和平台超管能查看能力、工作方式、技能库、提示词、工作配置和岗位档案。
- 运营管理层与普通员工只看到派活、本人/授权范围内进度和业务结果；服务端执行时仍锁定并注入完整岗位能力，执行能力没有缩水。
- 餐饮员工、Paihuo 内容员工和工具箱统一增加内部档案防泄漏封条与结果检查。若模型被要求复述内部提示词或供应商异常回显，受限角色只得到安全提示，结果契约失败、附件清空，不能采纳、发布或进入后续业务流。
- 内容员工的完整岗位上下文进入 system，当前业务任务单独进入 user，避免把内部档案与用户材料混成一段。

## 六、UI 升级内容

设计方向参考 Apple 的清晰层级与内容优先、Claude/Claude Code 的任务—过程—产物分离，以及 Linear 的弱导航、命令入口和 inspector 结构。没有照搬品牌外观，而是转化为适合中文实体门店经营场景的 Quiet Command。

### 全局壳层

- 从顶部、左栏、右助手、底栏四边常驻，改为默认“可收起导航 + 主工作区”两栏。
- 经营助手改成按需 Drawer，默认关闭。
- 移除常驻底部快捷条，低频动作进入命令面板。
- 使用瓷白画布、石墨正文、单一钴蓝动作色和克制状态色。
- 支持键盘焦点、窄屏与 `prefers-reduced-motion`。

### 任务指挥台

- 标题区直接说明当前角色的动作，不再只是静态指标卡。
- 任务卡区分“执行记录”和“业务流”。
- 管理层可从进行中的上级任务打开“拆解给员工”，成员来自正式 `/api/execution/assignees` 组织范围接口。
- 一线员工不显示新建、拆解或审核入口。
- 审阅意见、重开原因、上级任务和父子关系都在界面可见。

### Paihuo 内容生产仓

- Paihuo 内容部门正式进入内容生产仓，显示真实在岗人数、自动规则和待审核数量。
- 十名内容员工改为“岗位列表 + 当前岗位 inspector”，主动作始终是打开该员工工作台。
- 手动创作、立即自动和定时任务仍是三个真实生产方式，不把十个工位画成已经自动串行的假流水线。
- 老板/管理员保留完整岗位内部档案；运营与普通员工只看到派活和业务结果，能力不打折但查看权限不越界。

### 餐饮数字员工与目录

- 目录减少说明性卡片，筛选、分部和员工选择成为主层级。
- 员工卡改为三列桌面布局，并提供 3→2→1 响应式变化。
- 工作台的运行记录新增业务流入口；完整七面板只属于老板侧管理视图。

## 八、真实云 API 边界

本轮没有把本地模板输出冒充真实云结果。旧测试密钥已经在历史会话中暴露，因此本轮明确不复用。当前完成的是“真实应用 API、权限、数据库、状态和界面链路”验收；老板参谋、餐饮数字员工、内容员工三个代表性云端文本质量样本，必须等待一枚轮换后的新测试密钥后再执行。

拿到新密钥后的停止条件：最多三个生成请求；禁图片、视频、支付、飞书和外部发布；任何模板降级、契约失败、超时、悬挂占扣或模型路由错误都立即停止。
