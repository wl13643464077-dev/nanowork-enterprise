# 04 · 路线图与验收标准

## 一、三期路线图

假设团队配置：**2 名前端 + 2 名后端 + 0.5 设计**。若人力更少，按每期内的优先级顺序砍尾部。

### 第一期：止损与立信（3 周）

**目标**：让产品在客户深度使用后不会被认为团队在撒谎；UI 从"一眼廉价"到"专业克制"。

| 周 | 后端 | 前端 |
|---|---|---|
| W1 | 删/改全部假数据与占位（`analysis.js:574` 的 `SELECT 1`、`assets.js:466` 估值默认值、`baseline.js:50` 客单价 8000）；工具箱接真 AI 或标注模板模式；async handler 全部套 `asyncRoute()` | 建 design token 层（`theme.css` 扩充）；删登录页 `LIVE_SIGNALS`；`System.tsx:766` RAG 宣传改条件渲染 |
| W2 | 51 个死接口逐个决策（接通/删除/flag）；接通飞书扫码绑群 + 数据来源地图；`growth.js:381/523/534` 改 scoped 查询 | 重写登录页动效（CSS mesh + 进场编排）；抽 `AuthShell` 统一 Login/Register/Pending；删 AI音频 Tab |
| W3 | AI 主通道加指数退避重试；模型可用性巡检；清理双份 env 加载器 | **接通餐饮员工派活入口**（纯前端接线）；5 处 CSS 模板字符串搬进 .css；换掉 5 个整页静默的 `.catch(()=>{})` |

**第一期验收（硬性）**：
- [ ] `rg '#[0-9a-f]{6}' web/src --glob '!theme.css' --glob '!data/*'` = **0**
- [ ] `rg 'const STYLES = ' web/src` = **0**
- [ ] 登录页无 canvas，无任何编造数字，动效全部带缓动，响应 midnight 与 reduced-motion
- [ ] 60 位餐饮员工在 UI 上可派活，任务状态可轮询查看
- [ ] 死接口数从 51 降到 **0**（接通或删除，flag 的记入白名单）
- [ ] `docs/` 与 README 中 6 条假宣称全部修正（见 `00-总览` 第五章）
- [ ] `npm run verify` 全绿（后端测试 + typecheck + 隔离扫描 + 生产构建）

### 第二期：真数据与真闭环（6 周）

**目标**：经营数据不再靠手填 Excel；能自动收钱；RAG 不再有 500 文档天花板。

| 周 | 后端 | 前端 |
|---|---|---|
| W4 | 迁移基建（`0002-*.mjs` 起，含 up/down + 执行器） | 修长任务反馈（`api.stream` 推广 + 后台任务 hook + 取消按钮） |
| W5-6 | 第一批 4 张表（`stores`/`dishes`/`order_items`/`costs`）+ 进 `check-isolation` 监控 + `dataintake` 支持导入 | 补键盘可达性与 focus-visible + 装 `eslint-plugin-jsx-a11y`；修可读性（字号/对比度/emoji） |
| W7 | 基于新表实现真实客单价、菜品销量排行、菜单工程四象限、毛利率、盈亏平衡点；修 `dashboard.js` 的 `||` 双源短路 | 新增菜品/成本/门店管理页；驾驶舱补毛利与客单卡片 |
| W8 | RAG 重构（预筛 + LIMIT + 移出主线程）；`kb_citations` 进 `initSchema`；`embed-backfill` 补进度与断点 | 加骨架屏；9 处轮询加 visibilityState 门控；`Employees.tsx` 70 卡加 memo |
| W9 | 接微信支付 + 支付宝（含回调验签、幂等、对账、退款）；补 recharge 测试 | 充值页改真实支付流程；业务数据 Excel 导出（接 `skillrun.js` 渲染器） |

**第二期验收**：
- [ ] 迁移文件从 1 个增到 5+ 个，`migrateV2()` 冻结不再新增
- [ ] 新增 4 张表全部在 `check-isolation.mjs` 的监控列表内，扫描无高危
- [ ] 驾驶舱能显示真实客单价与毛利率（有成本数据时）
- [ ] 菜品销量排行不再靠 `GROUP BY o.product` 文本分组
- [ ] RAG 在 2000 文档规模下单次检索 < 800ms 且不阻塞其他请求
- [ ] 支付全链路可用：下单 → 扫码 → 回调 → 积分到账，含重复回调幂等测试
- [ ] 客户列表 / 订单 / 活动 / 资产台账 / 经营分析均可导出 Excel
- [ ] 无任何 AI 操作让用户盯着无进度转圈超过 5 秒

### 第三期：差异化与规模化（8 周）

**目标**：建立竞品无法快速复制的能力；能承接连锁客户。

| 周 | 内容 |
|---|---|
| W10-13 | **抖音生活服务 OpenAPI 接入**：开发者认证 → 生活服务应用 → 到店餐饮解决方案权限 → 商家授权链路 → 门店映射 → 团购商品映射 → 核销（prepare/verify/cancel/get/query）→ 对账（核销记录/分账/账单）→ 会员绑定同步 |
| W12-14 | **企业微信集成**：客户联系、群机器人推送、私域会员同步（可与抖音并行） |
| W14-16 | **10 个高价值餐饮岗位补输出契约**（复用 `content-output-contract.js` 模式）：营销、选品、成本、排班、点评回复、私域、活动、培训、供应链、选址 |
| W15-17 | **多门店 / 连锁总部视图**：跨店对比、总部一键全店报表、区域汇总（对标美团品牌驾驶舱） |
| W16-17 | 换掉 DuckDuckGo 联网搜索（国内商业 API + 多源 fallback）；第二批表（会员储值/排班/库存/评价） |
| W17 | 拆分超大文件（`content.js` 3240 行 → 5 个子路由；`ContentFactory.tsx` 2701 行 → 按 tab lazy）；枚举统一下发；公共校验层 |

**第三期验收**：
- [ ] 至少 1 家真实商家完成抖音授权并成功核销，数据回流到 dashboard
- [ ] 至少 10 个餐饮岗位有独立 JSON 输出契约与字段校验
- [ ] 连锁场景：1 个租户下多门店可独立看数据 + 总部可汇总
- [ ] 单文件行数上限 1200 行（当前最大 3240）
- [ ] 前后端枚举单一来源，无双份维护

## 三、风险与注意事项

### 3.1 高风险项

| 风险 | 影响 | 应对 |
|---|---|---|
| **抖音接入需服务商资质 + 逐商家授权** | 不是纯技术工作量，可能卡在资质审批数周 | 第三期启动前先走完认证流程；同期准备美团 POS ID 映射方案作为备选 |
| **`node:sqlite` 是实验性 API + 同步调用** | 生产环境高并发下写锁竞争；RAG 场景已暴露阻塞事件循环问题 | 第二期至少把重计算移出主线程；评估迁 PostgreSQL 的成本（涉及 74 张表 + 858 处查询调用） |
| **模型名疑似别名占位** | `gpt-5.5`、`gemini-3.1-flash-lite`、`deepseek-v4-flash`、`gpt-image-2`、`claude-opus-4-8`。任一失效 → 对应角色全部降级到模板，用户看到的是模板文案而非 AI 输出 | 第一期加模型可用性巡检 + 告警；在 UI 明示当前实际使用的通道 |
| **`migrateV2()` 近 800 行无回滚** | 补 8 张表若在此函数内继续加会推到 1000+ 行不可维护；且任何迁移失败无法回滚 | 第二期 W4 必须先建迁移基建再动数据表，顺序不可颠倒 |
| **竞品免费策略挤压** | 客如云 2026 春耕计划免费开放五大智能体；美团智能掌柜免费且有真实数据 | 必须走 `00-总览` 的路线 A（收缩定位）或路线 C（治理层），不要在"AI 助手 + 看报表"上正面竞争 |
| **删除死代码的连带风险** | 51 个死接口中部分有测试（如 `agents.js` 有 `custom-agent-access.test.mjs`）；删接口需同步删测试与表 | 逐个决策时先跑 `npm run verify` 确认基线，删除后重跑 |

### 3.2 不要动的地方

以下是项目真正的工程资产，改动需格外谨慎：

- `engines/two-phase-delivery.js`（169 行）+ `engines/credits.js`（295 行）—— 两阶段计费，有 6 个专项测试守着
- `engines/scheduler.js`（238 行）—— 原子认领 + 重启恢复，有 2 个专项测试
- `db.js:565-600` 的三层隔离机制（INSERT 自动注入 / scoped 禁裸 OR / AsyncLocalStorage）
- `index.js:254-263` 统一错误处理（不泄堆栈、有 requestId、处理 headersSent 与客户端断开）
- `util.js:20-25` scrypt 密码哈希（校验路径异步化的工程考虑正确）
- `auth.js:137,142` jti 会话列表 + `users.auth_version` 即时吊销
- `content.js:3108-3160` 幂等发布登记（`idempotency_key` + `BEGIN IMMEDIATE` + 冲突 409）—— 接支付时直接复用这个范式
- `seed.js:394` + `index.js:48` 的 SEED_DEMO 生产门禁（有 `seed-gate.test.mjs`）
- `hooks/useQuery.tsx`（93 行）四态 + 防竞态 —— 不要重写，要推广
- `api/client.ts` 的超时分级、SSE、CSV 注入防护
- `Employees.tsx:167-178` 的骨架屏与 a11y 实现 —— 作为其他页面的模板
- `Dashboard.tsx:24-34` 的 `interactiveRow` —— 同上
- `engines/toolbox.js:26-73` 的 `INPUT_SCHEMAS` DSL —— 要提取推广，不要删

### 3.3 流程建议

1. **每期结束跑一次完整审计**：`npm run verify` + `node scripts/check-isolation.mjs` + 重新统计本报告的量化指标（硬编码颜色数、内联 style 数、死接口数、`.catch(()=>{})` 数），把数字变化写入 CHANGELOG
2. **建立防回归**：token 层建好后，加 CI 检查禁止新增硬编码颜色；装 `eslint-plugin-jsx-a11y`；关掉 `allowEmptyCatch`；把 `chunkSizeWarningLimit` 从 1600 降回 800
3. **文档与代码同步**：本次审计发现 `docs/纳米Work行业版-整合规格.md:79` 说测试 252/252，`docs/最终验收记录-2026-07-25.md:76` 说 341/341 —— 两份文档数字冲突。建议文档不固化易过期数字，改为引用命令输出
4. **每期做一次真实用户测试**：找 2-3 位真实餐饮老板（35-55 岁）实际操作，重点观察：能否在 5 分钟内看懂驾驶舱、能否独立完成一次派活、字号是否够大、AI 等待时是否会以为卡死
