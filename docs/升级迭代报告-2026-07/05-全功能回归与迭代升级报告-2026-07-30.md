## 五、数字员工完整性与输出质量

### 5.1 档案层：结构完整

核验结果：

- 60 名餐饮数字员工均有岗位档案、输入、执行步骤、交付物、质量门和安全边界。
- 10 名 Paihuo 内容员工均可加载。
- Paihuo 共 45 项锁定能力。
- 70 名员工共 409 张技能卡。
- 趋势官完整工作台的六个页签全部可见。
- 70 份岗位派活引导均为岗位化文案，没有复用错位的食材成本示例。

这一层可以判定为“档案完整”。

### 5.2 执行层：完整配置没有全部生效

Paihuo 自动/定时任务存在能力降级：

- 工作配置只被写进提示词。
- 实际模型仍由固定岗位映射决定。
- 输出上限固定为 3,000 tokens。
- 超时固定为 85 秒。
- 趋势、调研、拆解等 `webRequired=true` 岗位不执行联网检索。
- 手动工作台和自动化走不同执行逻辑，导致同一个员工在不同入口能力不一致。

真实趋势官样本验证了这一点：它透明说明无法进行实时网页搜索，没有伪称已联网，这是安全上的正向表现；但它仍给六个渠道写了“无明显信号”并给候选话题打了高/中/低热度，只能算待核验草案，不能算完成热点情报扫描。

### 5.3 输出契约层：校验无效

对 10 套内容员工输出契约做反例测试：

- 趋势官：全部必填值为 `null`，通过。
- 调研官：全部必填值为 `null`，通过。
- 拆解官：全部必填值为 `null`，通过。
- 文案官：全部必填值为 `null`，通过。
- 风格官：全部必填值为 `null`，通过。
- 多媒体官：全部必填值为 `null`，通过。
- 封面官：全部必填值为 `null`，通过。
- 分发官：全部必填值为 `null`，通过。
- 复盘官：全部必填值为 `null`，通过。
- 网页演示官：因 HTML 必须非空而拒绝。

当前校验主要检查“有没有这个 key”，没有检查：

- 值是否非空。
- 类型是否正确。
- 数组是否有最小数量。
- 数组项目是否有完整结构。
- 来源、时间、证据是否真实存在。
- 是否满足员工自己的质量门和放行条件。

60 名餐饮员工则没有对应的机器可验证岗位 Schema，主要依赖提示词和风险扫描。

### 5.4 数据层：多数记录不是可交付内容

数据库内容分布：

| 内容类别 | 数量 | 判定 |
| --- | ---: | --- |
| 真实 API 输出 | 1 | 有真实文本，但未完成联网岗位要求 |
| 通用“待企业核验的内容草案” | 120 | 占位底稿，不是成品 |
| “待企业核验的岗位交付草案” | 10 | 只有交付说明，不是岗位成品 |
| 自动任务契约底稿 | 4 | 只证明调度和契约落库，不是实际产出 |
| 合计 | 135 | 只有 1 条可进入真实内容质量复核 |

这些模板记录保持“待审核”是正确的安全边界，但系统不能把它们计入：

- 员工完成量。
- 内容生产成果。
- 内容效果榜。
- 经营成效。
- 对外演示中的“自动生产完成”。

### 5.5 技能和连接器

- 409 项历史技能全部标记为 `legacy_unverified`，说明结构已导入，但能力真实性尚未逐项验收。
- 10 名 Paihuo 员工中有 7 名专属连接器仍为 `catalog_only`。
- 目前不能宣称十个岗位的专业生产链已经全部真实接通。

## 六、缺陷与风险分级

### P0：发布阻断

#### P0-1｜所有外部 AI 调用没有统一成本与并发保护

工具箱、活动、增长、文件 OCR、知识库 OCR、餐饮员工派发、内容自动化和 RAG 等路径没有全部进入统一的预检、占扣、结算、失败释放、速率限制和并发控制。部分后台任务在 HTTP 响应结束时就释放并发位，但真实 AI 仍在运行。

影响：

- 上游产生真实费用，企业积分可能不扣或超扣。
- 多请求并发可绕过余额检查。
- 后台任务数量失控。
- 账单、任务与审计日志无法一一对账。

#### P0-2｜Paihuo 自动任务能力降级

位置：`server/src/routes/content.js:812-958`。

自动化没有真正应用员工模型、输出长度、超时和联网配置。真实趋势官输出已经证明 `webRequired` 未兑现。

#### P0-3｜输出契约不能证明产出完整

位置：`server/src/engines/content-output-contract.js:182-219`。

9/10 岗位的必填值全部为 `null` 仍通过；餐饮员工没有严格 Schema。

#### P0-4｜启动调度器可能自动产生费用

位置：`server/src/index.js:271-288`。

带真实密钥启动服务后会立即扫描并领取到期规则。没有显式维护模式、调度总开关和启动前费用确认。

#### P0-5｜密钥与上游错误处理不安全

- 管理后台把完整密钥明文存入 SQLite。
- 界面“脱敏存储”只是回显掩码，描述不实。
- 上游错误文本可能原样进入 HTTP、日志或数据库。
- 本轮使用过的密钥已经出现在会话中，必须撤销或轮换。

#### P0-6｜未完成底稿被当作内容成果

134/135 条内容不是实际岗位交付。若继续进入效果排行、员工产量和对外演示，会形成错误经营认知。

### P1：高优先级业务问题

#### P1-1｜销售读取全租户老板日报

销售账号访问 `/api/dashboard/daily-digest` 返回 200 和全租户经营数据；相邻老板简报、管理和内容汇总接口均正确返回 403。

#### P1-2｜执行目标百分比失真

2026 年 7 月和 Q3 没有目标记录，实际收入为 369,108 元。代码使用：

`pct(actual, g.revenue_target || 1)`

0 目标被替换为 1，页面显示 `36,910,800%`。正确行为应为“目标待设置/不可计算”，不能生成百分比。

#### P1-3｜销售移动端存在无权限入口

销售角色只开通驾驶舱和执行模块，但移动端仍固定显示：

- 餐饮数字员工
- 经营工具箱
- 内容生产仓
- 经营分析

今日简报显示“加载失败：无权限执行此操作”，点击内容生产仓会被重定向回首页，形成死入口。

#### P1-4｜平台超级管理员角色冲突

- 路由允许 `platform_super` 进入 `/admin`，`Admin.tsx` 又拒绝。
- `Recharge.tsx` 支持 `platform_super`，路由又只允许老板。

#### P1-5｜工具箱没有继承完整员工能力

工具箱只带员工姓名，没有加载岗位档案、技能、工作配置、质量门、安全边界、审批和计费策略。同租户用户还可能看到其他用户的工具运行结果。

#### P1-6｜门店和支付业务完整性不足

- 订单明细缺少幂等键和批量事务。
- `grossMargin` 扣除了人工、租金、水电和营销，更接近经营利润率。
- 订单没有 `store_id`，多门店收入归属不准确。
- 主动查单响应没有严格验签。
- 本地取消没有关闭渠道订单，可能出现“用户已支付但本地已取消”。

#### P1-7｜页面失败态不一致

活动、执行、分析、资产、管理等多个钻取和配置请求在失败后会吞错、永久加载或缺少重试，不满足 loading / empty / error / retry 四态要求。

### P2：工程质量与可观测性

- 严格 ESLint 有 199 条警告，主要是键盘可访问性、静态元素点击、无效锚点和 effect 更新。
- 46 个文件未通过格式检查。
- Vite `advancedChunks` 已废弃。
- 云雾失败指标没有正确累加。
- 启动日志只识别部分供应商，可能把云雾误报成模板模式。
- 内容媒体任务存在两组重复路由。
- 租户隔离扫描还有 36 处动态查询待人工确认。
- 多处列表存在 N+1 查询风险。

## 七、迭代升级路线图

### 迭代一：成本、密钥与调度安全

目标：任何外部调用都必须可限额、可追踪、可退款、可停止。

改造项：

1. 建立唯一 AI Gateway，文本、搜索、图片、视频、OCR、Embedding 全部通过同一入口。
2. 所有调用统一执行权限检查、余额预检、积分占扣、并发占位、上游请求、结算或释放。
3. 后台任务的并发位必须保持到真实任务终态，不能在 HTTP 响应结束时释放。
4. Scheduler 默认关闭；只有明确环境开关和启动预检通过后才运行。
5. 增加租户、用户、模型、单次 tokens、每日金额和总金额上限。
6. 密钥只通过环境或密钥服务注入，不允许明文写 SQLite。
7. 上游错误统一脱敏，清除 Authorization、`sk-` 型凭据和已知指纹。

验收标准：

- 全仓扫描不存在绕过 Gateway 的上游调用。
- 并发 10 次请求时积分不负数、不重复扣费、不产生未记账费用。
- 401、429、500、超时、断流和坏 JSON 均释放 hold。
- 启动服务不会自动产生外部请求。
- Canary 不出现在 HTTP、日志和数据库。
- 数据库和备份不存在明文 API Key。

### 迭代二：完整员工执行引擎

目标：同一个数字员工从任何入口执行时能力完全一致。

改造项：

1. 合并手动、立即、定时、工具箱和餐饮员工派发的执行入口。
2. 执行请求真实采用员工的模型、输出长度、超时、联网、工具、审批和质量门配置。
3. `webRequired=true` 必须执行真实检索，并把来源、日期、证据和失败状态写入结果。
4. 联网失败时任务状态应为“待补证据/未完成”，不能标记正常产出。
5. 为 10 名 Paihuo 员工建立严格 JSON Schema。
6. 为 60 名餐饮员工建立岗位级 Schema 与质量证据。
7. 工具箱加载完整岗位档案，并做创建人/角色结果隔离。

验收标准：

- 修改员工模型、长度、超时后，上游实际 payload 与配置完全一致。
- 10 个 Paihuo 岗位的空值、错类型、缺字段和空数组全部拒绝。
- 60 个餐饮岗位每个至少有一份合法样本和五类非法反例。
- 必须联网的岗位没有来源时不能进入“待审核成品”。
- 手动、立即、定时、工具箱四条路径对同一任务给出一致快照和质量门。

### 迭代三：权限与业务逻辑

目标：每个角色只看到能做的事，所有经营指标都有正确业务语义。

改造项：

1. 老板日报增加老板/管理员角色与数据范围检查。
2. 目标为 0 或缺失时显示“待设置”，不计算完成率。
3. 移动端工作台按角色模块过滤，权限失败显示可行动的空态。
4. 统一 `platform_super` 在 `/platform`、`/admin`、`/recharge` 的产品边界。
5. 订单增加幂等键、事务和 `store_id`。
6. 拆分毛利率、贡献利润率和经营利润率口径。
7. 主动支付查询严格验签，取消时同步关闭渠道订单。
8. 所有页面统一 loading / empty / error / retry 四态。

验收标准：

- 销售无法读取任何老板级全租户聚合数据。
- 目标缺失时前后端均返回可解释状态，不出现伪百分比。
- 每个角色的桌面端和移动端入口与模块权限一致。
- 平台超级管理员的路由、页面和接口权限矩阵一致。
- 订单重复提交不重复累计；批量失败全部回滚。
- 支付重复通知幂等，坏签名拒绝，取消后渠道单不可支付。

### 迭代四：数据与发布质量

目标：演示数据、真实产出、技能能力和发布质量可以清楚区分。

改造项：

1. 模板底稿状态改为“未生成/待补材料”，不计入产出和效果榜。
2. 逐项验证 409 个 `legacy_unverified` 技能，记录版本、来源、适用岗位和验收样本。
3. 把 7 个 `catalog_only` 连接器改为真实可调用或明确标记“未接通”。
4. 严格 ESLint 警告清零，格式检查通过。
5. 为 analysis、assets、growth、platform 补端到端覆盖。
6. 修复废弃构建配置、重复路由、失败指标和 N+1 查询。
7. 增加真实输出抽检：事实性、岗位匹配、证据、可执行性、安全边界。

验收标准：

- 未完成底稿不会进入员工完成量、内容成果和效果排名。
- 所有对外可见技能均有验收记录，不再把未核验目录当已具备能力。
- 严格 lint、format、typecheck、test、build 全部通过。
- 关键模块路由行覆盖率不低于 80%，关键权限/计费链有真实端到端测试。
- 至少完成 10 个 Paihuo 岗位和代表性餐饮岗位的真实小额验收样本。

## 八、建议的发布关口

只有同时满足以下条件，才可以从 NOT GO 改为 GO：

- P0 全部关闭。
- 本轮已暴露密钥完成撤销或轮换。
- 所有外部调用进入统一 Gateway。
