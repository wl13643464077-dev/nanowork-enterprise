## 0. 一页纸摘要

**这次要解决什么：** 客户拿同一个问题（“北京望京商圈餐饮的客单价是什么范围，有哪些代表的店，再具体看下火锅及火锅相似竞品”）同时问豆包和我们的「钱商圈」。豆包 57 秒给出了分档表、二十多家店和竞争小结；我们只抓到 3 家店，满屏“待核验 / 未获取”。客户由此得出结论：“数字员工跟豆包差不多，甚至不如。”

**根因不是模型不行，而是架构把所有问题都当成同一种题来做。** 代码里有五个结构性原因（详见第 2 节）：

1. **一个模板管所有题。** 61 个员工、每一次派活，都要填满同一个 `restaurant-role-output/4` JSON 契约：逐条输入核查、逐步方法执行、全部 5 份交付物、质量复核、安全复核、审批。快查题被做成一份 4 分钟的重型岗位报告，篇幅都花在“过程证明”上，真正回答问题的部分反而最少。
2. **取证“窄而严”。** 一次联网调研最多取 12 条结果，还会把榜单、聚合页当 SEO 过滤掉；高德只取离中心最近的 10 家同品类店。可“有哪些代表店”这种问题，恰恰最需要广覆盖。
3. **员工用不到客户自己的数据。** `marshalWork` 不读取本企业已导入的订单、菜品、日报、评价（这些数据只给驾驶舱和分析页用）。我们唯一的数据护城河，数字员工根本没碰到，所以输出自然和豆包差不多。
4. **不问、不记、不让改。** 提示词明确写着“不得反问老板”；业务参数（预算、目标、价格带）缺失时只能瞎猜或标“待核验”。企业也没有办法把“我的城市、品类、竞品名单、输出偏好”固定下来复用。
5. **会分析和会干活是断开的。** 分析页没有“派给某员工”的入口。

**升级思路，一句话：** 先判题型，再按题型取证和组织答案。广度用公开检索补，深度用客户自有数据补，个性化用企业偏好补；输出是老板改几个数就能用的草稿，不是格式化报表。

**本期范围：61 位餐饮员工 + 内容仓员工全部升级。** 分两档：
- **L1 全员升级（全部 61 位 + 内容仓）**：题型路由、按题型答题形态、去公式化、来源分档、广覆盖检索、自有数据按需注入、假设面板与“我的版本”、技能补充包（只追加）、每人 ≥2 条标准问法（进题库，可一键填入）、分析派单映射、每人 ≥2 道回归金标题。
- **L2 A 级深做（8 位，见第 4 节）**：在 L1 基础上，专属题型技能卡、专属形态变体、自有数据深度接入、演示 SOP 与样例结果、每人 5 条标准问法、5 道金标题，并与豆包盲评对比。

不新增业务模块，不新增智能体。

**v2.2 补充的两个判断（来自通读技能卡与全网调研）：**
- **现有技能卡约 1/3 是海外口径。** 食安部大量引用 FDA、加州 SB-68、纽约法规；品牌部引用 Google 商家资料、Instagram、Yelp、FTC；财务部用美元基准（如 SPLH 45 美元）；连锁部引用美国 EPAct、PFAS。对 3–15 家店的中国连锁，这些卡给不出能直接执行的答案。另有约 15 张卡依赖系统拿不到的数据（窄门餐眼、外卖 3 公里订单、袋鼠参谋），161 查巡巡一张卡都没有。**处理方式：原卡一张不动，追加中国本土补充卡（FR-6、附录 D）。**
- **平台已经把“单店问答”做成免费品。** 美团智能掌柜已覆盖约 130 万餐饮商家，2026-10 又向全国外卖商家免费提供“妙手外卖版”AI 店长。数字员工不能再卖“问一句答一句”，要卖平台不做的三件事：**跨平台的数据合在一起看、站在总部看多家店、分析完直接产出可执行的东西并派给下一个员工**（第 1.5 节）。

**成功标准（摘要）：** 望京原题在我们这里覆盖 ≥15 家店、≥4 个价格档、90 秒内出结果，并且盲评胜过或持平豆包；8 个 A 级员工的金标题集盲评胜/平率 ≥70%；正文中不再出现“方法覆盖 n/n”“输入完整性”这类过程字段。

## 1. 背景与目标

### 1.1 会议确定的定位（不变）

- **AI 经营分析：保下限。** 它对标美团智能掌柜、店参谋等，属于获客钩子，不和美团比大而全，比的是“小而精、快”。
- **数字员工和内容生产仓：保上限。** 这是差异化，要能直接交付结果，形成“分析 → 干活”的闭环。
- **定价锚定岗位工资**（9,900 元/年），卖的是可复制的总部能力，不按软件定价。
- **不加新模块，不加新智能体。** 61 个岗位太散，挑 6–8 个往深里做。

### 1.2 客户的质疑（逐条记录，本 PRD 要正面回应）

| # | 客户原话（来源：逐字稿 / 李颖转述） | 本 PRD 的回应 |
|---|---|---|
| Q1 | “美团免费的就有，再加个豆包就能实现” | 数字员工必须用上**客户自有数据和企业偏好**，并且能**派活和执行**，这两点是豆包做不到的（FR-5、FR-7、FR-8） |
| Q2 | “数字员工数据都是公网抓的，我用豆包也能抓到” | 公开检索要做到**比豆包更广、更准、有来源**（FR-4），再叠加**豆包拿不到的数据**（自有数据、高德结构化数据、品牌知识包） |
| Q3 | “出来的和豆包差不多，只抓到 3 家店” | 按题型路由和答题形态（FR-1、FR-3），加上覆盖度门槛（FR-4.4） |
| Q4 | “还需要自己喂资料、自己训” | 品牌知识包、自有数据自动注入，加上“我的版本”偏好持续累积（FR-5、FR-7） |
| Q5 | “自由度不高，不能自己编排” | 不加智能体，但允许企业**在员工内部改参数、存偏好、改假设重算**（FR-7） |
| Q6 | “数据真实吗？” | 每条事实都标来源和可信档位；拿不到的，明确告诉老板缺什么、怎么补（FR-4.5） |

### 1.3 本期目标

- **G1：** A 级员工在同一问题上，对比豆包或通用大模型时胜出或持平，并且每份输出都带有本企业专属信息（可以测量，见第 9 节）。
- **G2：** 输出不再公式化。不同题型对应不同形态；老板改一个假设就能重算；企业偏好可以沉淀下来。
- **G3：** 销售和代理商能稳定演示：样例数据、固定演示话术，只换店名，不翻车。
- **G4：** 分析结果能一键派给对应员工，形成闭环。

### 1.4 全网调研：AI 在餐饮已经解决了什么（2026-11-20）

**行业底数。** 红餐产业研究院调研显示，我国餐饮行业的 AI 应用渗透率约 15%，预计 2028 年到 50%；2025 年全国餐饮企业注册量 240 万家，同比下降 14%，存量超过 1,600 万家；2025 年四季度厨师、服务员月均薪资分别为 6,777 元、4,884 元。行业已进入存量竞争，降本增效是第一课题。连锁化率从 2020 年的 15% 升到 2024 年的 23%。

## 2. 现状诊断（代码证据）

> 以下全部来自对本地快照的读码。路径相对 `server/src/`。

### D1 · 所有员工、所有问题共用一个重型输出契约（“公式化”的直接原因）

- `engines/restaurant-output-contract.js`：`SCHEMA_VERSION = "restaurant-role-output/4"`，顶层字段固定为 `contract_id / role / decision_context / input_audit / method_execution / deliverables / quality_review / safety_review / approval`。
- `buildContract(employee)` 按员工目录的 `inputs`、`steps`、`deliverables` 逐项生成必填字段。以钱商圈（idx 102）为例，**每次**都必须填写：4 项输入核查、7 步方法执行、5 份交付物。这 5 份交付物是“商圈边界与需求发生器清单、竞品/替代品矩阵、餐段人流与竞争强度热表、评价主题与菜单宽度对标、三个机会空白与实地调研计划”。
- 假设字段被强制写成“具体岗位角色 + 核验动作 + 截止时间”同一句话（`ASSUMPTION_VERIFICATION_DESCRIPTION`），于是每份报告都会出现大量“商圈研究员于 X 日前核对……”这类句子。
- `renderRestaurantOutputMarkdown` 渲染出的结构固定为：老板结论 / 关键证据 / 风险与缺口 / 下一步 / 任务范围 / 关键假设 / **岗位执行完整性（输入完整性、方法执行记录）** / 岗位完整成果（逐份交付物：报告正文、证据、动作、验收）/ 附录（质量、安全、授权）。61 个员工全部一样。
- 演示租户的 report-first 路径（`engines/restaurant-report-first-validation.js`）仍然强制要求“方法覆盖 7/7”和“方法 n”执行表。
- 成本和时延：完整岗位单轮输出上限 20k tokens；代码注释记录健康单轮约 200–265 秒，失败时整单约 1,000 秒；47.5 KB 的 schema 曾导致 DeepSeek 网关 502/504（注释里的任务 #43）。8/07 三视角评审已经提出“按模型档位放宽契约”，但没有落地。

**结论：** 契约的初衷是保证专业和诚实，这一点要保留。但它把过程证明变成了每一份答案的主体，并且不区分题型。望京这道题其实只需要一张分档表加一份店铺清单，却被迫产出“餐段人流热表”“实地调研计划”这类拿不到数据的东西，自然满屏“未获取”。

### D2 · 没有“题型”概念，只有两条极端路径

- **派活路径**：`routes/marshals.js` 中的 `POST /:id/tasks` 调用 `dispatchMarshalTask`，再调用 `engines/ai.js` 的 `marshalWork()`，走的是重型契约，加上联网和高德。
- **对话路径**：`marshalChat()` 是分部级对话，**没有联网检索**，`maxTokens: 1800`，按分部身份作答。
- 没有任何地方先判断“这是快查题、诊断题，还是方案题”。快查题要么走重型路径，要么走无检索的对话路径，两条都不对。

### D3 · 公开取证“窄而严”，高德只取最近 10 家

- `marshalWork` 发起一次 `agenticWebResearch`（`maxResults: 12`）。查询文本是一大段指令，而不是多个检索角度。
- `engines/public-source-quality.js`：地点类任务会剔除 `seo_ranking_or_unrelated_aggregation`（榜单/聚合）和营销页，并要求通过任务相关性过滤。但“代表店有哪些”这类信息，主要正是从榜单、聚合页、团购页拿到的线索。
- `engines/location-intelligence.js`：`TRADE_AREA_TOP_N = 10`；`topCompetitors` **按距离排序**取前 10。品类检索最多取 2 组关键词、3 页、每页 25 条；人均依赖高德 `biz_ext.cost`，这个字段经常为空。
- “相似竞品”（烤肉、串串、冒菜）没有专门检索。只有当用户写的品类关键词恰好命中时，才会进入竞品集合。
- 高德客户端（`engines/amap.js`）：全进程共享节流器，**串行间隔 1.1 秒**，排队超时 60 秒。一次商圈任务大约要 10–20 次请求；几个任务并发时，排队超时会被判为 transient 失败。凭证、配额、IP 白名单错误（10001/10003/10005/10009）会直接中断，不再重试。

> 会上演示时商圈、人流、人均、营业时间大面积“未获取”，可能是以下任一原因：①线上 `AMAP_WEB_KEY` 未配置或类型不符；②服务器 IP 不在白名单；③日配额用尽；④并发排队超时；⑤高德对这些 POI 本来就不返回 cost 或营业时间。**本地快照无法判断是哪一个，需要按 FR-4.3 的自检脚本在线上确认。**

### D4 · 数字员工不读取客户自有经营数据（“和豆包差不多”的根本原因）

- `marshalWork()` 里**没有任何**对 `orders / dishes / daily_ops / reviews / stores` 的查询。这些表只被 `routes/dashboard.js`、`analysis.js`、`advisor.js`、`store-data.js` 和 `engines/daily-digest.js` 使用。
- `content-store-facts.js`（门店事实包）只接入了内容生成（`generateContent`），没有接入 61 个餐饮员工。
- 品牌知识包（24 维）会通过 `kbSearch → brandMatchExcerpts` 注入，最多 3,200 字。但它只覆盖品牌层信息，不含经营数字。

**结论：** 王菜单做菜单优化时看不到这家店的菜品销量和毛利，葛会员看不到会员和复购，钱商圈不知道“你家人均多少”。我们唯一比豆包多的东西，没有被用上。

### D5 · 技能卡是“文字提示”，部分依赖拿不到的数据源

- `catalog/employee-skills.json` 共 409 张卡，每个员工约 6 张，状态全部是 `legacy_unverified`。
- 以钱商圈为例：“窄门餐眼导出竞品对比表”“调取外卖平台近半年 3 公里订单数据”“高德扫街榜排名”，这些数据系统都拿不到。卡片会诱导模型去“要”这些数据，最后只能标“待核验”。
- **v2.2 逐张通读后的结论**（汇总见附录 D 开头）：约 1/3 的卡是海外法规或平台口径；约 15 张依赖拿不到的数据；锚点定价在 108/111/112 重复，Prime Cost 周追踪在 106/150/154 重复，AI 视觉秤在 129/148 重复；161 查巡巡为 0 张；全员都缺“读老板自己的导出表”和“按题型作答”两项通用能力。
- 卡片受指纹门禁保护：`content-source-parity` 等测试锁定派活源 SHA，`employee-skills-verification.js` 校验快照 `614631…`。直接改 JSON 会让测试失败，也会破坏磊哥多轮调试的结果。代码里已有先例：`engines/poster-text-capability.js`、`engines/content-xhs-playbook.js` 都是“目录不动、运行期注入”。

### D6 · 不追问、不记偏好

## 5. 方案总览

```
老板一句话（+可选附件）
        │
   ① 题型路由 Intent Router（FR-1）──→ 题型 / 实体槽位 / 缺失参数 / 置信度
        │
   ② 追问闸门（FR-2）── 只问“业务决策参数”，最多 3 个，可跳过（跳过就按显式假设继续）
        │
   ③ 证据编排（FR-4、FR-5）
        自有数据包 → 品牌知识包 → 企业偏好 → 高德结构化 → 广覆盖公开检索
        └─ 覆盖度门槛：不达标就换角度补检；仍不足时明说缺多少、怎么补
        │
   ④ 按题型生成（FR-3）── 快查 / 诊断 / 方案 / 产物 / 完整报告（瘦身后的旧契约）
        │
   ⑤ 可改输出（FR-7）── 假设面板改值重算 · 换形态 · 存为“我的版本”
        │
   ⑥ 派单出口（FR-8）── “下一步派给 XX” 按钮，带上下文一键派活
```

**设计原则：**

1. **先判题，再取证，再成文。** 不同题型在形态、时长、成本上的预算都不同。
2. **诚实保留，过程后置。** 质量、安全、来源校验照常在后台跑，但不再占据正文。正文只放答案；“工作底稿”默认折叠。
3. **广度靠检索，深度靠自有数据，个性靠偏好。** 豆包只有第一项。
4. **缺什么就说什么、怎么补。** 不再出现无解释的“待核验”。
5. **复用现有的计费、权限、风控、版本机制。** 任何新路径都必须走两阶段积分和 `scanText` 风控。

## 6. 功能需求（FR）

> 每条都写明：做什么 → 放在哪 → 验收点。新文件建议放在 `server/src/engines/` 下，测试放在 `server/test/`。

### FR-1 题型路由（Intent Router）

**新文件：** `engines/employee-intent-router.js`

**输入：** 员工 idx、任务标题和要求、附件元数据、租户是否有自有数据、是否演示租户。

**输出：**
```json
{
  "type": "lookup | diagnose | plan | produce | full_report | team",
  "confidence": 0.0,
  "entities": { "city": "北京", "area": "望京", "category": "火锅", "related_categories": ["烤肉","串串","韩餐"], "price_band": null, "brand": null, "store": null, "period": null },
  "missing_business_params": [{ "key": "budget", "label": "活动预算", "default": "按营业额3%估算" }],
  "answer_shape": "lookup.market_scan",
  "reason": "问句为“范围/有哪些/看下”，对象是外部市场事实"
}
```

**题型定义：**

| 题型 | 判定信号（示例） | 默认时长和成本预算 | 是否用旧契约 |
|---|---|---|---|
| `lookup` 快查 | “是什么 / 多少 / 范围 / 有哪些 / 哪家 / 看下”，对象是外部市场事实 | ≤90 秒（P50），输出 ≤4k tokens | 否 |
| `diagnose` 诊断 | “为什么 / 哪里出问题 / 下滑 / 异常”，对象是自家经营 | ≤120 秒 | 否 |
| `plan` 方案 | “怎么做 / 帮我设计 / 策划 / 规划”，没有要求完整报告 | ≤150 秒 | 否 |
| `produce` 产物 | “写 / 生成 / 出一份 SOP、菜单、文案、考题、话术” | ≤150 秒 | 否 |
| `full_report` 完整报告 | 明确说“完整报告 / 可行性研究 / 给投资人看”，或者是高风险决策（签租约、开新店投资），或者用户在结果页点了“升级为完整报告” | 沿用现状 | 是（瘦身后，见 FR-3.6） |
| `team` 协同 | 跨 3 个以上岗位，或者“一句话组队” | 沿用协同小队 | 沿用 |

**实现要求：**
- 规则优先，模型兜底。先用关键词和句式规则打分，置信度 <0.7 时再调一次低价文本模型分类，结果需过 JSON 校验，超时 5 秒就回落为规则结果。
- 每个员工配置**允许的题型白名单**。例如钱商圈 = lookup / diagnose / full_report；柏带训 = produce / plan。命中白名单外的题型时，自动推荐更合适的员工（复用 `specialist-matching.js`）。
- 路由结果写入任务快照（新字段 `intent_json`），工作台的“执行时间线”展示“判题：快查·市场扫描”。
- 前端在派活输入框下方实时显示预判题型，例如“将按【快查】回答，约 1 分钟”，并允许手动切换为“完整报告”。

**验收：** 金标题集（第 9 节）路由准确率 ≥90%；望京原题判为 `lookup`。

### FR-2 追问闸门（只问业务参数）

- **只在 `plan / produce / full_report` 题型，并且缺少的是“业务决策参数”时追问。** 业务参数指老板自己的意图或约束，例如预算、目标、时间、是否已有会员系统、目标客群。**可检索的事实**（地址坐标、竞品、营业时间）永远不问，自己去查。
- 一次最多 3 个问题。每个问题都带**默认值按钮**（例如“按营业额 3% 估算”），另有一个“跳过，按默认假设先出稿”。
- 演示租户、无人值守任务（定时、派单自动触发）和 `lookup / diagnose` 题型一律不追问，直接按默认假设执行，并在“假设面板”里显示出来。
- 企业偏好（FR-7.2）里已有的值，不再追问。
- 修改研究提示词：把“不得反问老板补……”限定为“可检索事实”，删掉对业务参数的禁令。

**验收：** 店小满题“帮我做个周末活动”会出现 ≤3 个带默认值的问题；钱商圈望京原题不追问。

### FR-3 按题型的答题形态（Answer Shapes）——去公式化的核心

**新文件：** `engines/employee-answer-shapes.js`。每种形态包含：Markdown 骨架、轻量 JSON 校验（只校验关键结构）、生成提示词片段、渲染器。

#### FR-3.1 `lookup.market_scan`（行情快查。望京原题即此类）

正文结构（按问题动态取舍，**不强制每节都出现**）：

1. **一句话结论**：例如“望京主力人均 80–120 元；火锅覆盖 40–180 元全价位，与韩式烤肉在 80–120 元正面竞争。”
2. **分档表**：档次 / 人均区间 / 典型场景 / 代表店（每档 2–4 家）。
3. **目标品类分层清单**：连锁主流 / 本地特色 / 新开或网红。每行写清店名、类型特色、人均、位置、来源档位（A/B/C，见 FR-4.5）。
4. **相似竞品**：抢同一预算、同一场景的替代品类，例如火锅对应烤肉、串串、冒菜、韩餐。
5. **竞争格局 3 条**。
6. **对你意味着什么**（豆包没有的部分）：如果有品牌包或自家价格带，就对比自家定位，指出空白和风险；没有的话，用一行提示“绑定你的门店后可对比”。
7. **口径说明**：人均来自哪类来源，团购价和点评人均的差异，数据日期。
8. **下一步按钮**：“让赵先机评估在望京开店机会”“让王菜单按竞品价格带调整菜单”“出完整商圈报告”。

**硬性要求：** 店铺清单 ≥15 家（区域级问题）或 ≥8 家（街道或商场级）；价格档 ≥3 档；每家店至少 1 个来源；正文 ≤2,500 字。

#### FR-3.2 `diagnose.store_issue`（诊断）

结论 → 关键数字（来自**自有数据**，标明口径和周期）→ 原因排序（每条写证据和可信度）→ 建议动作（≤5 条，每条可一键派给员工）→ 需要补的数据。
没有自有数据时，不硬诊断：明确说“需要导入近 30 天订单/菜品数据”，给出导入入口，同时基于公开信息给出“可能原因清单”，并标明是推测。

#### FR-3.3 `plan.action_plan`（方案）

方案草稿：目标 / 打法 / 时间表 / 预算 / 物料清单 / 风险。再加**假设面板**（预算、客单、转化率、天数等，可改），以及执行清单（事项 / 负责岗位 / 截止 / 验收）。
执行清单的“负责岗位 + 截止”规范只用在这里，不再污染其他题型的假设字段。

#### FR-3.4 `produce.artifact`（产物）

直接给成品（SOP、菜单文案、考题、活动海报文案、会员话术等），加 3 行使用说明，加“可替换字段”高亮（店名、价格、日期）。不附加方法执行记录。

#### FR-3.5 统一的“工作底稿”（折叠区）

原先放在正文里的内容，全部移到工作底稿（默认折叠，导出 Word/PDF 时可选是否附带）：输入核查、方法执行、质量复核、安全复核、来源全表、检索轨迹。

#### FR-3.6 完整报告瘦身（保留旧契约，但降负担）

- 交付物按意图**选 1–3 份**（路由给出 `selected_deliverables`），不再每次 5 份全出。
- `input_audit / method_execution / quality_review / safety_review` 改为**可选**字段，由服务端根据检索和校验结果自动生成，不再要求模型逐字填写。
- report-first 的“方法覆盖 n/n”硬校验改为警告级。
- `ASSUMPTION_VERIFICATION_DESCRIPTION` 只作用于方案类动作项。
- 目标：完整报告单轮输出 ≤12k tokens，健康耗时 ≤150 秒。

**反公式化校验（所有形态通用，新增到校验器）：**
- 正文中禁止出现以下过程术语：“方法覆盖”“输入完整性”“岗位执行完整性”“方法 n 执行记录”“contract”。
- 同一员工连续 3 次不同题型的输出，一级标题集合的 Jaccard 相似度应 <0.6（评测时统计）。
- 当本企业有品牌包或自有数据时，正文至少出现 1 处本企业专属信息（店名、菜品、价格带、数据点）。

**验收：** 望京原题按 FR-3.1 形态输出；第 9 节的反公式化指标全部达标。

### FR-4 证据编排：广覆盖检索 + 高德修复 + 覆盖度门槛

#### FR-4.1 多角度并行检索（快查和市场类）

- 根据路由实体自动扇出 6–10 条短查询（不要把长指令当查询词）。望京原题的示例：
  `望京 人均 餐厅`、`望京 火锅 推荐`、`望京 火锅 人均`、`望京 必吃 榜`、`望京 烤肉`、`望京 串串 冒菜`、`望京SOHO 餐饮`、`合生麒麟社 餐厅`、`望京 新开 火锅 2026`。
- 合并后最多取 30–40 个候选来源。复用现有的 `webSearch` / `agenticWebResearch` 通道和 360 检索。
- **榜单、聚合、团购页不再一律剔除。** 改为降级为 B 档“线索来源”，用于发现店名和人均区间；具体到某家店的关键事实，尽量用 A 档来源或高德补证。仍然剔除的有：翻译页、诈骗或站外联系方式、纯 GEO 获客软文、异地同名门店。
- 从来源正文中抽取结构化店铺实体（店名、品类、人均、地址或商场、来源 URL、日期），按店名加地理位置去重。

#### FR-4.2 高德采集扩展

- `TRADE_AREA_TOP_N` 10 → 30。排序从“纯距离”改为综合分：品类匹配 × 评分 × 距离衰减。距离最近的 5 家无论如何保留。
- **相似品类检索**：路由给出的 `related_categories` 各做一次关键词周边检索（每个最多 2 页）。
- 人均缺失时，用公开检索抽取的人均回填，并标注来源档位。

#### FR-4.3 高德故障修复与自检（M2，P0）

1. 新增 `scripts/amap-selfcheck.mjs`：用线上配置依次跑地理编码（望京SOHO）→ 周边（1,000 米，050000）→ 关键字搜索（望京 火锅）。输出 infocode、耗时、返回条数、是否带 `biz_ext.cost`。
2. 在管理后台“高德面板”（`AdminAmapPanel.tsx`）加入：今日调用量和配额、最近 20 次错误（infocode 加中文说明）、“立即自检”按钮。
3. 节流器改造：把“全局串行 1.1 秒”改为**令牌桶**（默认 3 QPS，可用 `AMAP_QPS` 配置），每个任务分配请求预算（默认 ≤25 次），排队超时改为按任务的剩余时长计算。凭证或配额错误要触发后台告警（站内信加飞书管理员推送，复用 `pushFeishuToManagers`）。
4. 高德整体不可用时，**不得**让商圈类任务输出大面积“未获取”。要自动切到 FR-4.1 的公开检索补位，并在口径说明里写清“本次地图数据不可用，店铺信息来自公开网页”。
5. 记录每日调用计数，接近配额（默认 80%）时，快查题优先走缓存（已有 24 小时缓存）和公开检索。

**验收：** 线上自检脚本 3 步全部通过；5 个商圈任务并发时，没有排队超时失败；人为把 Key 置错时，望京原题仍能输出 ≥15 家店（来自公开检索），并带明确说明。

#### FR-4.4 覆盖度门槛与二轮补检

- 每种形态都配置最低覆盖：快查·市场扫描是店铺 ≥15、价格档 ≥3、来源 ≥8。
- 第一轮未达标时，自动用不同角度补检一轮（换同义词、换商场名、换细分品类）。仍未达标时，正文顶部写明“本次只找到 N 家，原因……，你可以……”，而不是用“待核验”填满表格。

#### FR-4.5 来源可信档位（替代笼统的“待核验”）

| 档位 | 含义 | 展示 |
|---|---|---|
| A | 官方或一手来源：品牌官网、商场官网、高德 API、客户自有数据 | 直接使用 |
| B | 公开平台页、团购页、榜单、聚合页 | 正常使用，标“参考” |
| C | 模型推断、单一来源、日期超过 12 个月 | 标“推测”，不作为关键结论的唯一依据 |

正文中，每个数字或店铺后面都用上标或小字标档位，来源全表放进工作底稿。

#### FR-4.6 合规约束（红线，写进代码注释和测试）

- 不调用、不模拟美团/点评 App 端内接口，不做任何“抓取工具或插件”给客户用。
- 允许的范围：搜索引擎可索引的公开网页、高德开放 API、客户自行导出后上传的文件。
- 检索结果只抽取事实（店名、人均、地址、公开评分），不整段搬运原文。

### FR-5 自有数据进入数字员工（差异化的根本）

#### FR-5.1 员工自有数据包

- 新文件 `engines/employee-store-data-pack.js`。复用 `content-store-facts.js` 的思路，按员工需求汇总本企业或本门店的数据：
  - 王菜单：菜品清单、售价、近 30/90 天销量、成本卡（如有）、毛利、四象限草稿（复用分析页口径）
  - 葛会员：订单数、复购率、客单分布、会员数、近 30 天新客/老客、评价主题
  - 钱商圈 / 赵先机：自家门店地址、人均、品类、价格带（用于“对你意味着什么”）
  - 店小满：近 30 天营业额、客单、时段分布、历史活动效果（活动模块已有复盘）
- 数据包的格式是“口径 + 周期 + 数值 + 数据表来源”，上限 3,000 字。由 `marshalWork` 和新路径共同注入，用 `wrapUntrusted` 包裹。
- 在员工配置中声明 `dataNeeds`（新字段，写在 canonical profile 里），决定取哪些数据。
- 没有数据时，在形态里明确提示，并给出导入入口（深链到数据接入页对应模板）。

#### FR-5.2 演示租户样例数据（与 FR-9 联动）

罗二火锅脱敏数据导入演示租户（店名、人名、电话全部替换），确保 A3、A5 的诊断题在演示环境能跑出真实感的结果。

#### FR-5.3 品牌知识包采集优化（M12）

- 采集时同步生成“竞品对照”维度，抓取用户指定的 1–3 个竞品，以及按同城同品类自动建议的竞品。
- 维度状态清晰区分：“已采到 / 公开渠道无此信息 / 待老板补充”。“待老板补充”的维度支持一键上传或填写（解决代理商“还得自己喂”的反馈）。
- 采集完成后给出一页“知识包体检”：已填维度数、关键缺口，以及“补齐后哪些员工会更准”。

**验收：** 演示租户中，王菜单回答“我们的菜单哪些该砍”时，正文引用至少 5 个本店菜品和真实销量口径；没有数据的租户，显示导入引导而不是编造。

### FR-7 可改输出：老板改几处就能用（M4）

#### FR-7.1 假设面板与一键重算

- `plan / diagnose / lookup` 形态在 JSON 中返回 `assumptions[]`，每项包含 `{key, label, value, unit, source_tier, editable}`。例如：商圈半径 1.5 km、目标人均 90 元、活动预算 8,000 元、转化率 3%。
- 前端在结果顶部渲染为可编辑的小卡片。改值后点“按新假设重算”，调用 `report-refine` 引擎，传入结构化 diff 指令（不重新检索，只重算和改写），作为新版本保存。
- 快捷形态切换沿用现有 `REPORT_REFINE_QUICK_INSTRUCTIONS`，再新增“换成老板版（≤300 字）”“换成店长执行版”“换成表格”。

#### FR-7.2 “我的版本”（企业偏好，按员工保存）

- 新表 `employee_tenant_preferences(tenant_id, employee_idx, params_json, output_prefs_json, updated_by, updated_at)`。
- 可保存的内容：
  - 默认业务参数：城市、商圈、门店、品类、价格带、固定竞品名单、预算口径
  - 输出偏好：简短或详细、表格优先、口语化、必含栏目、禁用词
  - 固定附加要求：例如“所有方案都要给出店长执行清单”
- 入口有两个：①结果页“记住这些设置，下次自动用”（从当前任务的实体和假设一键生成）；②员工工作台“工作配置”面板新增“本企业默认设置”分组（出厂能力仍锁定，偏好只做追加，不削弱质量和安全规则）。
- 路由和追问阶段自动套用偏好，并在执行时间线上显示“已套用本企业默认设置（可修改）”。

### FR-13 老板提问 SOP 题库与“常用问法”（全员）

**目的：** 销售、代理和老板不用学怎么提问。挑一条标准问法，把店名、地区、品类这些词换掉，就是一个好输入。题库同时是演示 SOP、输入框联想和回归测试的唯一数据源。

- **数据文件：** `server/catalog/question-templates.json`（随本 PRD 交付，共 171 条：8 位 A 级员工各 5 条，其余 54 位餐饮员工各 2 条，内容仓 11 条；v2.2 新增 12 条“新规问法”，带 `addedIn: "v2.2"` 和 `basis`（依据的法规或平台规则及链接），分布见附录 F）。字段如下：
  ```json
  { "id": "emp102-q1", "employee": 102, "person": "钱商圈", "type": "lookup",
    "why": "想快速摸清一个商圈的行情，开店或定价前先心里有数",
    "template": "{城市}{商圈}商圈餐饮的客单价是什么范围，有哪些代表的店，再具体看下{品类}及{品类}相似竞品",
    "slots": [{"key":"城市","label":"城市","examples":["北京","成都","泉州"]}],
    "you_get": "客单价分档表、店铺清单、相似竞品、竞争格局、对你意味着什么",
    "tier": "A", "demo": true }
  ```
- **前端：**
  - 员工派活输入框下方展示该员工的“常用问法”标签（A 级 5 条，其余 2 条，有新规问法的员工多 1 条，标“新规”角标）。点击后填入模板，`{占位符}` 高亮成可编辑小块。
  - 优先用“我的版本”（FR-7.2）和门店档案自动填好占位符，没有值的保留高亮，提示老板替换。
  - 首页全局输入框：输入 2 个字以上时，按语义联想题库中的问法，并显示“由 XX 员工处理”。
  - 演示模式（FR-9）直接复用：选员工 → 选问法 → 填店名和地区 → 一键派活。
- **服务端：** 题库加载时校验占位符都在词典里、`type` 在员工的题型白名单内、员工编号存在。题库条目的 `type` 作为 FR-1 路由的强先验（通过问法发起的任务直接采用该题型）。
- **回归：** 题库每条问法用默认示例词填满后，就是一道回归题。CI 跑“路由题型一致 + 形态校验通过 + 反公式化通过”（不跑真实模型，跑 mock 生成）；预发环境每周用真实模型抽样 20 条。
- **配套交付物：** 《老板使用手册：数字员工提问 SOP 与 QA》PDF（给销售和客户），与本 JSON 同源生成，改题库时两者同步更新。
